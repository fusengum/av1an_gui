# 更新機能の設計

## 目的

ZIP を展開して使っている av1an_gui を、画面から新しい版に入れ替えられるようにする。
これまで「ファイルを更新したのに、動いているサーバーが古いコードのまま」という問題が何度も起きたため、
ファイルの入れ替え・ライブラリの更新・サーバーと画面の起動し直しまでを 1 つの操作で確実に行う。

## 決めたこと（利用者の回答）

- 配り方: ZIP を展開したフォルダ（.git は無い）
- 更新元: GitHub のリリース（タグ `vX.Y.Z` を付けて公開した版）
- 動かし方: 確認は自動（デスクトップ版を開いたとき・1 日 1 回）、入れ替えはボタン（デスクトップ版の見出し、Web 画面の「環境」タブ）
- 方式: 案 1（更新用の別プロセスで入れ替える）

## 版の番号と更新元

- フォルダ直下の `VERSION`（例 `0.4.0`）が今の版。`shared.version.app_version()` で読む。画面の表示・Web の `/api/meta` もこれを使う
- 更新元はツールの `app.json` の `"update": {"github": "owner/repo"}`。最初に見つかったものを使う。空なら「更新元が設定されていません」
- 最新版は `https://api.github.com/repos/{repo}/releases/latest` の `tag_name`。ZIP はリリースに付けた `.zip` があればそれ、無ければ `zipball_url`（GitHub が作るソースの ZIP）
- ZIP の中身が 1 つのフォルダにまとまっていれば（ソースの ZIP は `owner-repo-sha/` の下）、その 1 段を外す
- 確認の結果は `logs/update/check.json` に保存し、1 日以内なら取りに行かない（「今すぐ確認」は除く）
- テスト用に、環境変数 `AV1AN_GUI_UPDATE_SOURCE` にリリース情報の JSON ファイル（`tag_name` と `zip` のパス）を指定すると、GitHub の代わりにそれを使う

## 入れ替え（`python -m shared.update apply`）

GUI またはサーバーが ZIP を取ってきて `logs/update/new/` に展開し、更新用のプロセスを別に起動する。
更新用のプロセスは標準ライブラリと `shared.core.config` / `shared.web.client` だけを使う（PySide6 や FastAPI を読むと、
Windows ではその DLL を入れ替えられなくなるため）。

1. 処理中のジョブがあれば何もせずやめる（キューは止まっていても、待機があっても構わない。キューは保存されている）
2. Windows: このフォルダのサーバーと GUI のプロセスを止める（GUI が開いていたかを覚えておく）
3. 入れ替えるファイルを `logs/update/backup/` に退避する
4. 新しい版のファイルで上書きする。触らないもの: `settings*.json`、`logs/`、`tools/`、`.venv/`、`.git/`
5. 前の版の一覧（`logs/update/manifest.json`）にあって新しい版に無いファイルを消す（別リポジトリの拡張のファイルは一覧に無いので消えない）。初回は一覧が無いので消さない
6. `requirements.txt` の中身が変わったときだけ、ライブラリを入れ直す（`tools/uv` か PATH の uv、無ければ pip）
7. 外部ツールのセットアップ（`python -m shared setup`）を流す。入っているものは取り直さないので、増えたツールだけ取る。失敗しても続ける（注意として残す）
8. 新しい版の一覧を保存する
9. サーバーを起動する。GUI が開いていたら開き直す
10. Linux: サーバーは systemd が管理しているので、ファイルとライブラリを入れ替えてからサーバーのプロセスを止める（systemd が新しいコードで起動し直す）。`install.sh` が変わっていたら「`sudo ./install.sh` を実行してください」と注意を残す

3〜6 で失敗したら、退避したファイルを戻し、新しく増えたファイルを消し、ライブラリを入れ直していれば元の requirements で入れ直す。
そのうえで元の版のサーバーと GUI を起動する。

結果は `logs/update/status.json`（`state`: `done` / `failed` / `rolled_back`、`message`、`version`）に書き、
経過は `logs/update.log` に書く。GUI は次に開いたとき、この結果を一度だけ表示する。

## 画面

- デスクトップ版: 起動時と 24 時間ごとに裏で確認し、新しい版があれば見出しに「更新 0.4.0」ボタンを出す。押すと、リリースの説明を見せて確認したうえで ZIP を取り、更新用のプロセスを起動して自分は閉じる。エンコード中は「終わってから更新してください」と断る
- Web 画面の「環境」タブ: 今の版・最新版・「更新を確認」「更新する」。サーバーが ZIP を取り、更新用のプロセスを起動する（サーバーと GUI は入れ替えの間止まり、起動し直す）
- 設定画面の「外部ツール」タブにも、今の版と「更新を確認」を出す

## テスト

偽のリリース（手元の ZIP と JSON）と、作業用にコピーしたフォルダで試す。

- 新しい版を見つける / 同じ版なら見つけない
- 上書き・消えたファイルの削除・設定と logs は残す・拡張のファイルは残す
- requirements が変わったときだけライブラリを入れ直す
- ライブラリの入れ直しが失敗したら元に戻る
- 入れ替えの後、サーバーが新しいコード（指紋）で動いている
